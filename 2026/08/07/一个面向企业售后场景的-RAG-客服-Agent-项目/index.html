一个面向企业售后场景的 RAG 客服 Agent 项目

2026-08-07
项目作品

很多企业招聘页都会写一句：如果有个人主页、项目展示或技术博客会加分。

这句话以前我只是看过就算了。最近整理 GitHub Pages 个人主页时，我突然觉得，与其只在简历里列几个技术关键词，不如把真正做过的项目写清楚：为什么做、解决什么问题、系统怎么设计、哪些地方考虑到了工程化和生产边界。

这篇记录的是我最近整理的一个项目：面向企业售后客服场景的本地私有化 RAG + Agent 系统。

为什么做这个项目

企业售后客服不是一个单纯的聊天场景。

一个真实客服问题里，经常同时涉及：

  • 产品手册、故障排查文档和保修政策；
  • 订单状态、设备序列号和客户信息；
  • 售后工单、处理记录和人工升级；
  • 多轮对话里的上下文；
  • 权限、安全、日志和降级。

如果只做一个“上传文档然后问答”的 RAG Demo，很容易停留在玩具级别。它可以回答几个知识库问题，但很难说明系统如何接入业务数据、如何保护敏感信息、如何在模型不可用时继续提供服务。

所以这个项目的目标不是做一个只有聊天框的演示，而是做一个可以本地运行、可以演示、也方便继续扩展的企业客服 Agent MVP。

系统做了什么

这个项目把客服场景拆成了几条主线。

第一条是知识库问答。系统支持导入 TXT、Markdown 和 PDF 文件，经过解析、切分、Embedding 和 FAISS 索引后，客服可以基于产品知识库进行问答。回答会返回来源信息，包括文档、chunk、分类、页码、相关度和摘要，避免“模型说了但不知道从哪来”。

第二条是售后业务工具。Agent 可以查询订单、设备、保修状态和售后工单。模型不会直接碰数据库，也不会自己拼 SQL，而是通过业务服务调用 Repository。这一点很重要，因为企业系统里模型应该被限制在清晰边界内。

第三条是多轮会话。系统通过 session_id 管理上下文，支持历史裁剪、清空和 Redis 故障回退。即使 Redis 不可用，本地演示也可以退回到进程内存储。

第四条是内部工作台。项目用 Streamlit 做了一个客服工作台，包含问答、知识库管理、检索测试、会话历史和系统健康页面。这样它不只是 API，也有可以直接展示的界面。

技术架构

整体采用模块化单体架构：

我比较看重的一点是边界划分。

  • app/api 只处理 HTTP 路由、Pydantic 契约和统一响应；
  • app/agent 负责意图判断、检索和工具编排；
  • app/services 承载知识库生命周期和售后业务规则；
  • app/repositories 封装 MySQL、SQLite 和内存实现；
  • app/providers 封装 LLM 和 Embedding；
  • app/rag 处理文档解析、切分、Prompt、安全边界和来源信息；
  • app/memory 管理 Redis 或内存会话；
  • app/security 处理鉴权、角色权限和脱敏；
  • streamlit_app 提供内部客服工作台。

这样做的好处是，不同运行模式可以组合切换。默认可以完全离线启动，使用 Mock 业务数据、确定性 Embedding 和规则降级；接入本地 vLLM、MySQL、Redis 或 BGE 时，不需要改 API 层和业务服务层。

Agent 如何回答问题

一次客服请求大致会经过这些步骤：

  1. FastAPI 完成身份认证，并创建 request_id。
  2. ChatOrchestrator 根据输入识别订单、工单、保修或知识问题。
  3. 业务问题调用 BusinessService 查询结构化数据。
  4. 知识问题通过 Embedding 和 FAISS 召回相关 chunk。
  5. 系统把会话历史、检索证据和业务事实放进带安全边界的 Prompt。
  6. vLLM 基于证据生成最终回答。
  7. API 返回回答、引用来源、工具轨迹、降级原因和延迟。

当前 Agent 使用可预测的 Python 编排来做意图路由和工具选择，vLLM 只负责基于证据生成最终回答。这个选择比较保守，但对企业业务系统更稳：模型不会绕过服务边界，也不会直接执行高风险操作。

安全和降级

做客服 Agent 时，我不希望系统表现得像“模型什么都能答”。这个项目里有几条安全约束：

  • 知识库写操作只允许 admin；
  • 客户角色查询业务数据时要做资源归属校验；
  • 手机号、地址等敏感字段在日志或返回结构中脱敏；
  • 用户输入、知识片段和业务字段都按不可信数据处理；
  • 没有证据时要求模型明确无法确认，而不是编造；
  • vLLM 不可用时返回规则型或证据型降级答案；
  • Redis 不可用时退回进程内会话；
  • 数据库或工具不可用时保留已获得信息，并建议人工处理。

这些还不能替代完整的生产安全审计，但至少说明系统不是只围着“模型回答”打转，而是考虑了企业场景里绕不开的边界。

我想展示的能力

这类项目放在个人主页上，不只是为了说“我会 RAG”。

我更想展示的是这些能力：

  • 能把一个具体业务场景拆成知识、业务数据、会话、权限和运维几条线；
  • 能用清晰的 Repository / Provider 边界组织代码；
  • 能让项目在 Mock、SQLite/MySQL、内存/Redis、本地 vLLM 等模式间切换；
  • 能处理 RAG 的来源追踪和无证据拒答；
  • 能考虑降级、日志、健康检查和测试；
  • 能把项目做成别人可以启动、可以演示、可以继续扩展的形态。

对招聘来说，技术栈当然重要，但更重要的是项目能不能说明“这个人知道系统为什么要这样设计”。

后续计划

这个项目目前仍是 MVP。后续如果继续做，我会优先补这些方向：

  • 接入真实 BGE 中文 Embedding，并建立检索评测集；
  • 增加订单、客户和工单管理后台；
  • 接入企业身份系统和更细粒度权限；
  • 增加 Prometheus 指标和持久化审计查询；
  • 增加混合检索、reranker 和查询改写；
  • 接入真实 ERP、OMS、WMS 或工单系统；
  • 做并发、故障恢复和安全压测。

小结

以前做项目，更多是为了把功能跑起来。现在整理到个人主页上，我会更在意另一个问题：这个项目能不能让别人快速看出我的工程思路。

一个好的个人主页不一定要很华丽，但至少应该让访问者看到：我做过什么、为什么这样做、遇到问题时怎么取舍，以及下一步准备怎么走。

这篇博客就是一次尝试。后面我也会继续把能代表自己能力的项目整理出来，让主页不只是一个链接，而是一个更完整的技术作品集。
