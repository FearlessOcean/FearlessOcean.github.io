一个面向企业售后场景的 RAG 客服 Agent 项目

2026-08-07
项目作品
6.1k words
  • Agent
  • FastAPI
  • LLM

  • 项目展示

这是一个面向企业售后客服场景的本地私有化 RAG + Agent 系统。

项目把产品知识库、订单与设备数据、保修记录、售后工单和多轮会话整合到统一客服工作台中。后端通过 OpenAI-compatible API 接入本地或内网 vLLM，当前验证模型为 qwen2.5-3b；知识库和查询向量通过 Ollama 部署的 bge-m3:latest 生成，向量维度为 1024。

它不是一个只有聊天框的 RAG Demo。这个项目更像一个模块化单体 MVP：默认可以完全离线启动，也可以按需切换到 MySQL、Redis、本地 vLLM、Ollama BGE-M3 和 FAISS 等更接近真实环境的组合。接入这些基础设施时，API 层和业务服务层不需要跟着重写。

场景

企业售后客服的问题往往不是单纯的知识问答。

一个用户可能会问：“订单为什么还没发货？”、“设备无法开机怎么排查？”、“还在不在保修期？”、“能不能直接换新？”这些问题背后同时牵涉产品文档、订单状态、设备序列号、保修政策、工单处理记录和多轮对话上下文。

如果系统只会把文档丢进向量库再回答，它可以演示 RAG 的基本效果，但很难覆盖售后客服里真正麻烦的部分：结构化业务数据怎么查，权限怎么限制，模型没证据时怎么拒答，外部组件故障时怎么降级，客服人员怎么看到检索来源和工具轨迹。

所以这个项目从一开始就把目标定成“可运行、可演示、可继续扩展”的客服 Agent，而不是一次性脚本。

能力

项目目前包含这些主链路能力：

  • 私有模型接入：通过 OpenAI-compatible API 调用本地或内网 vLLM。
  • 本地语义向量：通过 Ollama 的 OpenAI-compatible API 调用 bge-m3:latest。
  • 知识库生命周期：支持 TXT、Markdown、PDF 的解析、切分、Embedding、增量导入、删除和重建索引。
  • 可溯源 RAG：回答返回文档、chunk、分类、页码、相关度和文本摘要。
  • 售后业务工具：查询订单、设备、保修状态和售后工单。
  • 多轮会话：以 session_id 管理上下文，支持历史裁剪、清空和 Redis 故障回退。
  • 权限控制：支持 API Key 或 Bearer Token，并区分 admin、customer_service 和 customer。
  • 安全回答：检索内容和用户输入都按不可信数据处理，无证据时要求模型明确拒答。
  • 可观测性：统一请求 ID、结构化日志、健康检查和进程内指标。
  • 内部工作台：Streamlit 提供问答、知识库、检索测试、会话历史和系统健康页面。
  • 部署入口：提供 Dockerfile、Docker Compose、环境变量模板和种子数据脚本。

架构

系统采用模块化单体架构：

代码边界按职责拆分：

  • app/api：HTTP 路由、Pydantic 契约和统一响应，不包含 SQL 或模型调用细节。
  • app/agent：意图判断、检索和工具决策、证据合并与回答编排。
  • app/services：知识库生命周期和售后业务规则。
  • app/repositories：MySQL、SQLite 与内存元数据访问实现。
  • app/providers：LLM 和 Embedding Provider 实现。
  • app/rag：文档解析、切分、安全 Prompt、FAISS 和来源处理。
  • app/memory：会话存储、历史裁剪和 Redis fallback。
  • app/security：鉴权、RBAC 和敏感字段脱敏。
  • app/observability：结构化日志与指标。
  • streamlit_app：企业内部客服工作台。

当前 Agent 使用可预测的 Python 编排完成意图路由和工具选择。vLLM 只负责基于证据生成最终回答，不直接执行 SQL，也不能绕过业务服务调用 Repository。这个边界是有意保守的：在客服这种业务系统里，可控性比“看起来更智能”更重要。

一次请求的数据流

一次客服请求大致会经过这些步骤：

  1. FastAPI 完成身份认证，并创建 request_id。
  2. ChatOrchestrator 根据输入识别订单、工单、保修或知识问题。
  3. 业务问题调用 BusinessService，由 Repository 查询结构化数据库。
  4. 知识问题通过 Embedding 和 FAISS 召回相关 chunk。
  5. 系统将会话历史、检索证据和业务事实放入带安全边界的 Prompt。
  6. vLLM 基于提供的证据生成回答；模型不可用时返回规则型或证据型降级答案。
  7. API 返回回答、引用来源、工具轨迹、降级原因和延迟。

这个流程里，RAG 不是单独存在的模块，而是和业务工具、会话记忆、权限控制、降级策略一起组成客服工作流。

安全与降级

客服 Agent 最怕“答得很像真的，但其实没有证据”。所以项目里做了几条基础防线：

  • 知识库写操作仅允许 admin。
  • 客户角色查询 SQL 业务数据时执行资源归属校验。
  • 手机号、地址和身份字段在日志或返回结构中使用脱敏值。
  • 用户输入、知识片段和业务字段都放入显式“不可信”边界。
  • 无知识证据时返回无法确认，不允许模型编造产品或政策事实。
  • vLLM 不可用时返回规则型或证据型答案，并设置 fallback_reason。
  • Redis 不可用时退回进程内会话。
  • 数据库或工具不可用时保留已获得的信息，并建议人工处理。

这些实现不能替代专业安全审计、网关 WAF、企业 IAM、凭据轮换和渗透测试，但它们让项目从 Demo 阶段就保留了向真实系统演进的边界。

当前边界

这个版本已经具备完整可运行主链路，但仍然是 MVP。生产上线前还需要补齐：

  • 企业 SSO、OAuth2/OIDC 和数据库账号密码登录。
  • ERP、OMS、WMS、物流平台和真实工单系统同步。
  • 订单、客户和产品的完整后台 CRUD 工作台。
  • 原生模型 Tool Calling 与更复杂的 LangGraph 状态图。
  • 持久化审计查询平台、Prometheus Exporter 和集中式告警。
  • 多 worker Redis 会话一致性与分布式任务处理。
  • 文档导入异步队列、失败重试后台和大规模索引分片。
  • BGE、vLLM 与真实业务数据上的离线评测集和性能压测。

小结

这个项目的核心价值不在于“接了一个大模型”，而在于把售后客服里的知识、业务数据、会话、权限、安全和降级放进同一个可运行系统里。

RAG + Agent 真正落到企业场景时，难点往往不是模型能不能说出一段流畅的话，而是回答有没有证据、业务查询有没有边界、组件故障时能不能退化、客服人员能不能看到来源和工具轨迹。这个项目就是围绕这些问题做的一次工程化尝试。
