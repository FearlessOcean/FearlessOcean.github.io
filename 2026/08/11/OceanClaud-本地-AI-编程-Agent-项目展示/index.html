OceanClaud：本地 AI 编程 Agent 项目展示

项目作品

OceanClaud 是一个使用 Python 3.12 实现的本地 AI 编程 Agent。项目围绕“让大模型在本地工程环境中可靠地调用工具、执行任务并保留运行证据”展开，核心目标不是只完成一次对话调用，而是搭建一套可观察、可扩展、可治理的 Agent Runtime。

项目采用双进程架构：前端 TUI/CLI 负责交互展示，后端 ocean-core 负责会话管理、模型调用、工具调度、权限审批、事件持久化和运行追踪。两者通过本地 TCP 通信，使用 JSON-RPC 2.0 承载命令，并以 NDJSON 形式传输请求、响应和事件。

项目定位

OceanClaud 面向本地编程助手与自动化研发场景，重点解决大模型从“会回答”到“能执行”的工程问题：

  • 将用户任务组织成可持续推进的多轮 Agent Loop；
  • 将文件读写、Shell、MCP、Skills、子代理等能力统一接入工具系统；
  • 在产生副作用之前完成权限判断和人工确认；
  • 将会话历史、运行事件和 Trace 持久化，支持回放、诊断和复现；
  • 在上下文增长后通过压缩机制维持长任务连续性；
  • 用统一事件流支撑 TUI 展示、任务重连和运行观测。

这个项目更关注 Agent 的运行时边界：模型如何拿到工具结果，工具如何被校验和审批，长任务如何恢复，错误如何暴露给用户，以及系统如何在扩展能力的同时控制风险。

系统架构

OceanClaud 将界面层和执行层拆开，形成一个轻量但清晰的本地 Agent 系统。

  • ocean-tui / ocean：负责用户输入、消息展示、token 状态、工具调用进度、权限请求和结果渲染。
  • ocean-core：作为常驻执行体，管理 session、run、模型 provider、工具注册表、权限系统、上下文压缩和事件写入。
  • SessionManager：维护会话状态，保证同一 session 的消息写入和运行创建有序进行。
  • AgentRunner：为每次 run 组装执行上下文、模型接口、工具系统、权限管理器、压缩器和事件总线。
  • AgentLoop：驱动“调用模型 -> 解析响应 -> 执行工具 -> 回填结果”的多步循环。

双进程设计带来的关键价值是生命周期解耦。界面可以退出、重连或切换，任务状态仍由 Core 持有；运行事件写入 events.jsonl 后，也可以被重新读取和回放。

执行链路

一次用户输入不会直接发送给模型，而是先进入 session 系统。TUI 通过 session.send_message 将消息发送给 Core，Core 路由到 SessionManager 后完成以下步骤：

  1. 检查 session 是否存在以及是否处于可写状态；
  2. 获取 session 级 asyncio.Lock，避免同一会话并发写入历史；
  3. 将用户消息追加到 thread.jsonl；
  4. 创建独立 run_id；
  5. 将本次运行交给 AgentRunner 执行。

Session 与 Run 是两层概念：一个聊天会话可以包含多次运行，每次运行都有独立事件、状态和任务记录。这样的结构既方便用户持续推进同一个上下文，也方便系统对每次执行进行追踪和诊断。

Agent Loop 的核心过程如下：

模型返回的 tool_use 会被解析为工具请求，工具执行结果再以 Anthropic 规定的 tool_result block 写回消息历史。下一轮模型能够看到真实观察结果，并决定继续调用工具、修正参数、切换方案或结束任务。

工具失败不会立即让整个 run 崩溃，而是以带 is_error 的结果返回给模型，让模型获得一次自我修正机会。同时，系统设置最大步数，避免任务陷入无限循环。

核心能力

1. 分层上下文管理

OceanClaud 的 system prompt 不是单一提示词，而是由多层上下文共同组成：

  • 基础角色提示词，或 Skill 覆盖后的提示词；
  • 用户级 ~/.ocean/context.md；
  • 项目级 .ocean/context.md；
  • 当前 session 的 notes.md；
  • thread.jsonl 中的消息历史。

系统还处理了一个容易被忽略的协议约束：模型生成的 tool_use 必须有对应的 tool_result。如果程序中途退出导致历史末尾只保存了 tool use，SessionStore 在重新读取时会裁掉这段未配对尾部，避免下一次 API 请求被判为非法。

当历史过长时，项目提供两道控制：工具输出在加载时截断，长上下文可通过 Compactor 整理为结构化 handoff summary。压缩结果会被重建为合法的 user/assistant 消息，让 Agent 能在较短上下文中继续运行。

2. 统一工具调用管线

工具调用不是直接执行函数，而是通过统一管线完成：

所有工具遵循统一的 BaseTool 接口。内置文件工具、任务工具、MCP 工具和子代理工具都可以进入同一个 ToolRegistry，并以统一 schema 暴露给模型。

统一管线也降低了 UI 的复杂度。界面不需要理解每个工具内部逻辑，只需要消费 tool.started、tool.finished、tool.failed 等事件，就能展示一致的运行状态。

3. 权限与副作用治理

OceanClaud 将模型输出视为不可信输入，在工具真正执行之前完成权限决策。

项目中的默认策略包括：

  • read_file、list_dir、note_save 默认允许；
  • write_file、bash 和未知工具默认询问；
  • bash 命中 deny pattern 时自动拒绝；
  • 命令疑似访问 cwd 之外的绝对路径、~、..、$HOME 或显式 cd 时强制询问；
  • 用户可以选择单次允许/拒绝，也可以持久化 always 策略。

其中一个重要细节是：cwd 外访问规则优先于 always 缓存。即使用户曾经允许过某类 bash 命令，新命令一旦触及越界路径，仍然需要再次确认。

这套机制适合作为应用层防线。对于生产级隔离，还需要结合容器、低权限用户、目录挂载白名单和资源限制。

4. Skills、MCP 与子代理扩展

OceanClaud 将扩展能力拆成三个维度：

  • Skills 扩展工作方式：通过 Markdown 文件定义专用提示词和工具白名单，用 /skill 参数 调用；
  • MCP 扩展外部能力：Core 连接 stdio 或 TCP server，发现工具后适配为普通 Tool；
  • 子代理扩展执行结构：创建独立上下文和 Agent Loop，可前台等待，也可后台并行。

内置子代理 profile 包括 planner、executor 和 reviewer。不同 profile 拥有不同提示词和工具白名单，例如 planner 适合读取、拆解和规划任务，但不应随意修改文件。

子代理默认不继承父对话，只接收显式 prompt。这样可以减少上下文污染，同时要求父 Agent 的委派描述足够自包含。系统还限制了嵌套深度，避免递归扩散。

5. 事件持久化与运行观测

OceanClaud 将运行过程本身视为产品数据，而不是只保存最终回答。

项目保留两类关键证据：

  • events.jsonl：面向一次 run 的业务事件，可用于 TUI 实时展示和重连回放；
  • Trace：记录 IPC、Event 和 LLM request/response 的时间线，用于定位慢点和异常。

当一次任务变慢时，可以基于 run_id 判断时间消耗在模型调用、工具执行还是权限等待；当结果异常时，也能回看工具参数、事件顺序和状态变化。

Trace 的完整 payload 对调试很有价值，但也可能包含源码、prompt 或敏感信息。更稳妥的生产默认策略应当是保存脱敏摘要，仅在诊断时临时开启完整 payload。

并发设计亮点

session.send_message 可能持续几十秒甚至更久。如果 SocketServer 在一个连接上顺序 await 每条命令，那么 Agent 发出权限请求后，用户的 permission.respond 可能会排在长请求之后，导致权限 Future 无法及时 resolve。

OceanClaud 的处理方式是：读到一行命令后立即创建独立 asyncio task，读取循环继续接收后续命令。这样同一连接上的权限响应可以并发到达 PermissionManager，避免跨层逻辑死锁。

这个细节体现了 Agent 工程中很重要的一点：交互式长任务不仅需要异步执行，还要保证控制命令能够穿透正在运行的任务链路。

验证结果

项目在 Linux 环境完成过复现；随后在 Windows 隔离工作树中做了不修改业务代码的检查，结果如下：

  • Mypy 检查 85 个源码文件通过；
  • WIRE_PROTOCOL.md 与当前 Pydantic 消息模型同步；
  • Ruff 报告 48 个既有格式或导入问题；
  • 单元测试 255 通过、7 失败，失败集中在 asyncio/pytest-asyncio 事件循环差异和 Unix sleep 命令；
  • 部分集成测试因隔离工作树没有复制包含密钥的 .env，Core 缺少 ANTHROPIC_API_KEY 而未启动。

这些结果保留了项目当前状态的真实边界：核心类型检查和大部分测试可运行，但跨平台测试、Shell 命令兼容性和集成测试环境仍需要继续收敛。

后续演进方向

OceanClaud 已经覆盖本地 Agent Runtime 的主要骨架。后续如果继续推进，优先级可以放在以下方向：

  1. 恢复机制：Core 启动时从磁盘恢复 session 索引，定义运行中断后的状态迁移；
  2. 取消传播：增加 run cancel，从 TUI 传播到 LLM stream、工具子进程和子代理；
  3. 执行隔离：在权限策略外增加容器/低权限用户、路径白名单和资源限制；
  4. 持久化一致性：引入原子写或 SQLite/WAL，并设计数据版本迁移；
  5. 跨平台 CI：固定关键开发依赖，在 Linux/Windows 上分别验证 shell 工具和 asyncio 行为。

项目摘要

OceanClaud 是一个 Python 3.12 实现的本地双进程 AI 编程 Agent。项目使用 Textual TUI、JSON-RPC/NDJSON IPC 和 Anthropic 流式 API，内置工具调用、权限审批、会话持久化、上下文压缩、MCP、Skills、子代理与 Trace。

它展示的是一个本地 Agent 从模型调用走向工程系统所需要的核心能力：清晰的执行链路、统一的工具管线、可控的副作用边界、可恢复的会话记录，以及面向调试和复现的运行观测。
